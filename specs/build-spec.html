00verdict

buildable: trivially yes — a weekend MVP, solo.

defensible: only if curation is the product, not a feature.

the engineering was never the risk. the swipe deck, the library, the "algo" are all solved patterns. what kills this product is sourcing tasteful images legally without importing the AI-slop you're trying to escape — and not getting eaten by cosmos. the differentiator is taste, and taste is manual labour, not an api call.

01what it is

a mobile-friendly web app. the core loop is tinder-for-images: you swipe through a stream of genuinely tasteful photos. swipe right and two things happen —

  • the image is saved to your personal library, to pull from later in real projects
  • it nudges a per-user taste vector so the next cards lean more toward your aesthetic

so: a taste-curation engine plus a reusable asset library, driven by swipe-to-train. the wedge nobody owns is all four at once — swipe as the primary input → personal taste model → reusable mood library → explicit anti-slop curation.

why pinterest is killed. its api only returns the logged-in user's own pins (sandbox-only on free tier) — it can't supply a firehose. the dev terms explicitly forbid "creating new content from pins" and list data extraction as unacceptable. scraping = terms violation + copyright liability (pins are other people's licensed-to-nobody images). and pinterest is where the slop lives — wrapping it imports the exact problem we're solving.

03the trap nobody warns you about

the two best legal image apis — unsplash & pexels — explicitly prohibit "an app that just serves images for users to save/download." a bare swipe-and-save gallery is the one pattern they ban.

this is the single most important finding, and it doubles as the strategy:

  • you cannot ship "just swipe + save unsplash photos" — terms violation, key revoked.
  • the fix is the product: wrap it in real added value (curation, mood-boards, project tooling, ai tagging) so it isn't an image downloader.
  • taste is not sourced, it is curated. no api hands you savee-tier images. the "super-tasteful" feel of cosmos/savee is human curation, not a data feed. that curation layer is the moat. everything else is commodity.

06the taste loop — it's ~20 lines, not a model

your note — "the right ones get aligned → makes the algo" — is exactly right, and far simpler than it sounds. there is no model to train. the running-mean update is the learning.

# the entire "algo"
on right_swipe(user, image):
    library.add(user, image)
    user.taste = running_mean(user.taste, image.embedding)   # ← this is it
    # optional: subtract a fraction of left-swipe means for a "dislike" pull

next_cards(user):
    ranked = pgvector_cosine(user.taste, pool minus user.seen, limit=20)
    return mix(ranked, random_diverse_sample, ratio=0.75/0.25)  # 25% explore
  • embeddings belong to the image, not the user — compute once, reuse across everyone.
  • store the taste vector as a float[] column; ranking = one sql ORDER BY embedding <=> taste_vector.
  • cold start: seed the first ~15 cards from diverse k-means buckets, frame it as a "calibration" moment. personalised feel kicks in around 15 likes, tight by ~40.
  • keep ~25% exploration permanently or you filter-bubble by swipe 5.
  • cost: $0–30/mo. anything fancier than this is solving scale you don't have. your real bottleneck is pool size, not the math.

07data model

profiles(id, taste_vector vector(768), created_at)
images(id, url, blur_data_url, width, height, embedding vector(768), created_at)
swipes(id, user_id, image_id, direction['like'|'skip'], created_at,
       unique(user_id, image_id))   # never show a card twice
saved_images(user_id, image_id, created_at, pk(user_id, image_id))

rls: swipes / saved_images readable only where user_id = auth.uid(). add an hnsw index on images.embedding. saved_images is redundant with liked swipes but makes the library view a trivial join.

08market — crowded but a real wedge

the tailwind

cosmos, savee, are.na are riding a genuine pinterest ai-slop exodus (sustained through late 2025). people are actively fleeing for human-taste-first tools.

closest competitor

buildwithtaste.com already does swipe → taste profile — but only UI screenshots for ai-coding. different lane. watch it.

the graveyard

"tinder for fashion" (mallzee, stylect) all died — on shopping monetisation, not the swipe. swipe-for-taste-profile is alive.

the threat

cosmos. owns your exact audience + brand, has the library + feed, could bolt on a swipe mode in a sprint.

positioning that writes itself: "human taste, trained by your swipes — the anti-pinterest reference library." who pays: the people already paying $7–15/mo for cosmos/savee/eagle — indie designers, art directors, builders who treat reference as a daily tool.

09build plan

phase 0 · 1–2h
scaffold. next.js 15, supabase project, schema + rls, seed ~300 hand-curated images (real urls, no embeddings), vercel deploy.
phase 1 · one weekend
MVP (~12–16h). motion swipe deck + like/nope overlays · prefetch-next-3 with decode + blur · candidate api (random order) · save endpoint · supabase auth · library grid · quiet-dark pass. prove the feel.
phase 2 · 1–2 days
taste ranking. wire clip embeddings, populate vectors, hnsw index, swap candidate query to cosine, update taste vector on each like.
phase 3 · ongoing
the moat. undo / super-save, collections, the curation + anti-slop layer, share/export, cost-optimised images.

10risks & open questions

  • legal the unsplash/pexels no-gallery rule is binding — the product must be more than a downloader from day one. this is design constraint #1.
  • moat cosmos can add swipe trivially. curation quality + the anti-slop stance is the only durable edge — invest there, not in the algo.
  • pool a genius ranker over 200 images still feels stale by swipe 50. an image-ingestion pipeline is more important than the recommender.
  • open name — "trove" is a placeholder. ("taste" is taken by buildwithtaste.)
  • open business model — free-to-~500-saves then $5–10/mo (cosmos/savee benchmark)?
  • open who's the sharp first user — your own reference workflow, or a public beta?
