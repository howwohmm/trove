code review & roast

trove · day-one adversarial review · 2026-06-07 · build: ✓ passing (19 routes, ts+lint green)

The rec-math and product shape are genuinely thoughtful. But the persistence layer is a house of cards: every store does read-modify-write with zero locking, and the swipe path fires three separate state writes that race each other — you will silently lose likes, library entries, and taste updates. Plus a real SSRF hole, non-atomic writes that corrupt your only copy on a mid-write crash, and a taste vector quietly polluted by AI images. A smart prototype with a data layer one fast-swiping session away from eating itself.

critical

C1 silent data loss — no lock on state.json

lib/store.ts · app/api/swipe/route.ts

A single like runs recordSwipe → saveImageFile → addToLibrary → updateTaste, each an independent read-modify-write of the whole state.json with awaits between. store.ts has no write-chain and no cache. Concurrent requests (fast swiping / keyboard arrows) clobber each other wholesale — last-write-wins on the entire object. Likes/library/taste vanish with no error.

Fix: one async mutex wrapping read+mutate+write as a critical section; ideally a single recordLike(candidate, vec) doing all three mutations under one lock + one write.

C2 SSRF + arbitrary write via request body

lib/store.ts saveImageFile · lib/embed.ts · lib/claude.ts

saveImageFile does fetch(url) on candidate.downloadUrl taken straight from the POST body, with zero validation, and writes bytes to disk. Server can be made to fetch cloud-metadata / internal hosts and persist arbitrary content. Embedding + Claude image blocks fetch attacker URLs too.

Fix: never trust the body — look the id up in the server corpus and use the stored URL, or allowlist picsum.photos/images.unsplash.com, https-only.

C3 non-atomic writes corrupt the only copy

store.ts:37 · dreams.ts:92 · facets.ts:46 · corpus.ts:29 · embeddings.ts:29

Every store is a single fs.writeFile(FILE, JSON.stringify(...)). Crash/disk-full mid-write → truncated file → next boot JSON.parse throws → catch silently resets to EMPTY. One bad moment wipes all swipes/library/taste.

Fix: write temp + atomic rename. Optionally keep a .bak.

high

H3 dreams pollute the real taste vector

app/api/dreams/swipe/route.ts:36

Keeping a generated dream folds the AI image's embedding into the same state.taste used to rank real candidates. Feedback loop → taste collapses toward your generator's own output. Silent. (Also: runningMean never decays — early swipes dominate forever.)

Fix: separate "dream taste" from retrieval taste, or don't fold generated images in at all.

  • H1 — module caches (dreams/facets) diverge from disk; markDream mutates the shared cache outside the exclusive() queue while a tick reads it.
  • H2 — getEmbedding's fire-and-forget void persist() can drop a late embedding; re-serializes the full 8MB map per embedding.
  • H4 — dreamId derives the next id from array max; "collision-proof" only by luck of the mutex, fragile if anyone generates outside exclusive(). Use a persisted counter / UUID.
  • H5 — every candidates GET rescans + rescores the whole corpus (up to 5000 × 512-dim cosines) on the request path. Cache scored array by tasteCount.
  • H6 — on the zero-config (picsum) path, picsum has no tags → taste-driven retrieval is dead; degrades to filtering the same 500 photos. The core loop only works with an Unsplash key.

medium & low

  • M2 — k-means random init → facet ids/labels reshuffle every recompute (every 5 keeps); a pinned facetId silently points at a different aesthetic. Need stable ids via centroid matching.
  • M3 — swipes array grows unbounded; state.json parsed twice per candidates GET. Cap/rotate; in-memory seen-set.
  • M4 — scheduleFacets/warmEmbeddings IIFEs lack .catch → unhandled rejection can crash dev server.
  • M5 — computeFacets "force recompute" silently no-ops if one is mid-flight, returns stale + ok:true.
  • L1 — dream-swipe embeds via a self-HTTP-fetch to its own /api/gen instead of reading local disk.
  • L5 — status polls OpenRouter /key every 8s; cache it.
  • N1 — Buffer.from(b64).buffer returns the pooled ArrayBuffer (may include trailing garbage); pass the Buffer directly.
  • N3 — Rocchio neg term subtracts even for negative cosine (rewards being opposite the dislike). Clamp to max(0, cos).

what's genuinely good

  • The rec architecture is real, not theater — multi-prototype (max over facet centroids) + maturity shrinkage size/(size+3) + Rocchio negatives + MMR with near-dup deferral is well-reasoned, and commented with the why.
  • The growing-corpus insight — decoupling "what we can rank" from the rate-limited source by persisting every fetched candidate + caching embeddings forever is the right core idea.
  • The exclusive() serial gen queue + tickDirty re-run coalescing is the correct instinct for the generation path.
  • Path-traversal guards on both image routes are present and correct.
  • Embeddings unit-normalized once so cosine = dot; k-means uses squared-euclidean knowing it ranks the same — a correct, deliberate optimization.
  • Consistent intent comments, mostly-honest types, graceful cold-start UX.

fix order

Before swiping more: C1 + C3. Serialize state.json mutations under one lock and make writes atomic (temp+rename). Right now the app can silently lose your only data. Then C2 (SSRF), H3 (taste pollution), then the H/M perf + correctness items.
